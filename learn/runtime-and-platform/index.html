Runtime and resource measurement

Separate processing time, latency, throughput, and utilization when judging whether an estimator keeps up with its input.

Learning objectives
  • Define the boundaries of a timing measurement

Define the operation and the processes measured

Processing time covers a named operation. Output latency spans a declared input event to a declared usable output, including any waiting inside that boundary. Throughput is completed work per unit time. Process CPU utilization and memory describe resource use; they are not interchangeable with elapsed processing time.

OpenVINS records timers inside VioManager separately from process resource polling. The upstream total spans its selected tracking, propagation, update, and marginalization work. Inspect the timer locations for the version used before including transport, decoding, visualization, or separate nodes in that total. Component intervals may overlap in other systems; adding them does not necessarily reconstruct a native total.

Compare distributions with input cadence

An illustrative 20 Hz camera stream has a 50 ms nominal interval. For stereo, define whether one processing event consumes a synchronized image pair. In a serial queue, sustained service slower than arrivals causes backlog unless inputs are dropped or throttled; concurrent processing requires measurements of the actual scheduling behavior.

Record mean, median, tail percentiles, and observed maximum, with the number of timed events and the included startup interval. Inspect queues, output latency, drops, and gaps. A mean below the input interval does not establish that every deadline is met. The observed maximum is limited to the measured run.

Preserve resource and aggregation conventions

Record device, operating system, CPU/GPU, power and thermal conditions, thread settings, build options, source revision, input interval, resolution, camera mode, and estimator configuration. State which processes are included, the polling interval, CPU percentage convention, and the memory quantity and units. Resident memory, virtual memory, and device memory are different measurements.

CPU percentages on different devices do not express equal computational capacity. Also distinguish a time-sample average, a pooled-event average, and an equal-weight mean of run summaries. Retain run counts and missing values. These reporting requirements do not redefine the native total, CPU, or process-memory fields in the published VIOBench snapshot.

Use profiling to investigate a measured cost

Internal timers identify expensive stages; a call-stack profiler helps locate work within them. Instrumentation changes runtime, so use profiled execution for diagnosis and repeat ordinary timing after a change. OpenVINS documents call-stack and memory profiling as separate developer workflows.

Keep the input, initialization outcome, estimated-trajectory extent, and accuracy checks alongside a speed comparison. Reducing processed frames, features, or state size can change both computational work and estimation quality. Report that changed condition with the measured result.

WORKED EXAMPLE

A 20 Hz serial input has a 30 ms mean processing time and a 90 ms high-percentile processing time. Is the mean enough to establish low-latency operation?

Explanation

No. The nominal interval is 50 ms, and some updates exceed it. Inspect queue behavior, output latency, and dropped inputs to determine whether the system catches up and meets the application's requirements.
