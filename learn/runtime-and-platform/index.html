Measure runtime on the platform you use

Separate processing time, latency, throughput, and utilization when judging whether an estimator keeps up with its input.

Define what the clock measures

Processing time measures an explicitly bounded operation, such as feature tracking plus an estimator update. End-to-end latency measures the delay from a stated input event to a usable output. Throughput measures completed work per unit time. CPU utilization describes processor activity. These quantities answer different questions, so a timing table should name its measurement boundary.

OpenVINS records internal component timings and total timings separately from process resource usage. An internal timer may exclude data decoding, transport, visualization, or another process. Determine what it covers before treating it as the cost of the entire application.

Look beyond the mean

For a stream at f images per second, the nominal image interval is 1/f seconds. At an illustrative 20 Hz, this is 50 ms. In a simple serial pipeline, sustained processing slower than the arrival interval produces a backlog or requires dropping work. Concurrent pipelines need measurements of the complete scheduling behavior.

Record a distribution: median, a high percentile, and maximum alongside the mean. Also inspect queue growth, output delay, dropped inputs, and gaps. A small mean cannot show whether occasional stalls violate an application's latency needs.

nominal image interval [ms] = 1000 / image rate [Hz]

Preserve the comparison conditions

Record the device model, operating system, CPU and GPU, power mode, thread settings, compiler, build options, and software revision. Keep image resolution, sequence interval, camera mode, and estimator settings with the result. Temperature and competing workloads can also change the observed runtime.

CPU percentages from unlike devices do not measure equal computational capacity. Compare systems on a common device when studying relative resource use, and use measured time and latency on each target device when studying deployment.

Profile a question, then measure the result

Component timing can reveal whether tracking, updates, or another stage dominates. A call-stack profiler can then locate costly functions. Profiling tools add overhead, so use their output to diagnose work and measure the changed application under the normal timing setup afterward. Keep accuracy and coverage checks with speed measurements: processing less useful input can make a system faster while changing its result.

WORKED EXAMPLE

A 20 Hz serial input has a 30 ms mean processing time and a 90 ms high-percentile processing time. Is the mean enough to establish low-latency operation?

Reveal the explanation

No. The nominal interval is 50 ms, and some updates exceed it. Inspect queue behavior, output latency, and dropped inputs to determine whether the system catches up and meets the application's requirements.
